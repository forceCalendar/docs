## Prerequisites

- Lightning Experience and **Lightning Web Security** enabled
- An org compatible with the package and API 62.0 metadata
- Salesforce CLI and an authorized org connection for CLI deployment
- A plan for activity permissions, sharing and related-record access

Legacy Lightning Locker is unsupported. Do not work around a missing custom-element API by weakening browser or org security.

## Option A: install the released unlocked package

Evaluate the release in a sandbox or disposable org before production rollout. Use the official installer for the target environment:

- [Production or Developer Edition](https://login.salesforce.com/packaging/installPackage.apexp?p0=04tg5000000ExTFAA0)
- [Sandbox](https://test.salesforce.com/packaging/installPackage.apexp?p0=04tg5000000ExTFAA0)

Or use Salesforce CLI:

```bash
sf package install --package 04tg5000000ExTFAA0 --target-org your-org-alias --wait 20
```

Review the CLI prompts and package details before installation. Installing does not automatically assign the optional permission sets or activate a Lightning page. The version is promoted, but installing it into any org is a separate administration action. No production-org installation is implied by the release or its clean-org verification.

## Option B: deploy the source distribution

Download the matching `forcecalendar-salesforce-dist.zip` from the [Salesforce releases](https://github.com/forceCalendar/salesforce/releases). Unzip it and deploy the generated Salesforce project:

```bash
cd dist
sf project deploy start --target-org your-org-alias
```

Deploy Apex, LWC and static resources as one matched set. Do not copy an arbitrary Interface UMD file into the org: the Salesforce build produces the combined Core/Interface resource and matching source layout.

## Build from source

From the [Salesforce repository](https://github.com/forceCalendar/salesforce):

```bash
npm ci
cd src && npm ci && cd ..
npm run build
npm test
cd dist
sf project deploy start --target-org your-org-alias
```

`npm test` builds the bundle and exercises the real component with mocked Apex transport. It does not execute Apex or prove LWS behavior in your org.

## App Builder and permissions

Drag **Force Calendar** onto an App, Home or Record page. Configure:

| Setting | Default | Options |
| --- | --- | --- |
| `currentView` | `month` | `month`, `week`, `day` |
| `height` | `800px` | CSS height |
| `readOnly` | `false` | Disable UI editing and LWC persistence callbacks |

Record pages supply the context record ID. Save/activate the page through your normal deployment process. Choose the minimum suitable [permission set](/docs/salesforce/permissions) and assign it only to intended users.

## Rollout checklist

- Confirm LWS and the installed package/source versions.
- Run `ForceCalendarControllerTest` and `ForceCalendarPermissionsTest` in the target test org.
- Test as intended readers/editors, including users with no related-object access.
- Confirm private/unshared records remain protected.
- Create a disposable timed event; edit it, cancel an edit, refresh, navigate and delete it.
- Test same-day/multi-day all-day dates and a DST boundary in your users' timezones.
- Check Contact/Lead and other supported record-page associations.
- Verify recurring events cannot be mutated here and `readOnly` blocks persistence.
- Inspect rejected writes and refresh failures without duplicating records.

No migration rewrites existing historical all-day records. If old data is wrong, investigate its source before deciding on a separate repair.
